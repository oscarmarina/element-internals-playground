# element-internals-playground

Lerna monorepo of Lit custom elements exploring `ElementInternals`. Packages in `packages/*`, scope `@blockquote-playground/*`.

## Commands

- Tests of one package: `npx lerna run test --scope @blockquote-playground/<pkg> -- --run`
- Tests of everything changed vs main (includes dependents): `npx lerna run test --stream --concurrency 1 --since origin/main -- --run`
- Lint (writes fixes): `npm run lint`
- Regenerate `custom-elements.json`: `npm run analyze` — never hand-edit it.

Tests run in Vitest browser mode on **chromium and webkit**, with `chai-a11y-axe` (`assert.isAccessible`). Coverage threshold is 80% — a failing threshold is a failing test. Playwright `getByRole` and axe compute names in JS and ignore `referenceTarget` / `ariaLabelledByElements`; only Chromium's AX tree (CDP) shows the real name. Assert it with `axNode()` from `test/ax-tree.ts` (see `*-ax-tree.test.ts` in `blk-input` and `blk-control`; Chromium only, skipped on WebKit).

## Invariants (breaking one is a bug)

- Errors are shown and announced only when the field is *user-invalid*, modelled on native user validity: a committed change (`input`/`change`) then blur, or an `invalid` event (form submission). Never on first render, key presses that don't edit, or — until the field has shown its error — programmatic value or constraint changes. In `blk-input` the gate is `__hasUserEdited`, not `touched`. Once the field has shown its error (`__hasReportedError`: an invalid blur after an edit, or an `invalid` event) every value change (typed or set by script: `update()`) and every constraint change (`required`, `pattern`, `disabled`…: `updated()`) re-validates until reset, so the error follows the validity. Neither ever raises the *first* error. This is the component's own policy (validate on blur, re-validate on edit), modelled on `:user-invalid` but not a replica of it: the inner control is not form-associated, so its `:user-invalid` cannot be read. `blk-control` follows the same policy with its own `__hasReportedError`: every `change` is already a committed choice, so the first error comes from the user's own `change` or an `invalid` event, and from then on `invalid` follows the native validity on every update (`updated()`). There `invalid` is only ever true while the native control fails: set on a valid control it is cleared on that update (unlike `blk-input`, which has `errorMessageText` to explain an external error); an external error goes through `nativeControl.setCustomValidity()`. It has no error text of its own: the page renders it, and `error-message-id` makes the input reference it with `aria-errormessage` while `invalid`. `blk-control-ssr` follows it too, with `:state(invalid)` instead of an `invalid` property; it does not observe attributes changed directly on the author's input, so it catches up on the next sync. Accepted differences: a `change` without blur (Enter that submits nothing) waits for the blur, and any `invalid` event counts (`checkValidity()` included). Do not chase native parity here. The native control always carries an explicit `aria-invalid` mirroring the host `invalid`, `"false"` included (`blk-input`, `blk-control`): left without it, browsers derive the state from native validity and expose the control as invalid before any interaction — a required unchecked checkbox/radio, a pre-filled value failing `type`/`pattern`/`min`/`max`, and in Firefox/Safari an empty required field. Honoured by Chromium (asserted in the `*-ax-tree` tests) and Safari (seen by hand); Firefox was seen ignoring it on a required radio, so there it is best effort. What is gated everywhere is what the component emits: host `invalid`, the visible error, its `role="alert"` and `aria-errormessage`. `blk-control-ssr` sets it on the adopted input too, once upgraded; server markup should carry `aria-invalid="false"` to cover the time before that.
- The native control lives in the shadow root. Its accessible name comes from `labelText`: host `aria-label` > `internals.ariaLabel` > associated `<label>` text, copied into `aria-label` at render time. When the shadow root has a `referenceTarget`, labels are **not** copied (the platform forwards them).
- Where `ariaLabelledByElements` is supported (and no `referenceTarget` or explicit aria-label applies), `blk-input` also points the control at its associated labels **once, when the control is created** (`_syncLabelReferences`), and again when the host `aria-label` changes. While the control references its labels, no `aria-label` is rendered (`_controlAriaLabel`), so translating a label's text updates the name without a render. Changes to *which* labels are associated are not observed — accepted limitation: a label associated later falls back to the copied text on the next render. Keep it simple: no observers, no per-update sync.
- `BlkInputReferenceTarget` sets `referenceTarget` in `willUpdate` from `_controlId`, before the first render; `hasReferenceTarget` must stay true as soon as it is set, even before the target exists. Never `requestUpdate()` from `updated()` to fix it up.
- `formDisabledCallback()` receives the *combined* disabled state; derive the fieldset part with `isFieldsetDisabled`, and recompute it in `willUpdate` when `disabled` changes.
- The reset value is captured once (first connect) or from the `value` attribute — moving the element in the DOM must not change it.
- `focus`/`blur` are composed: do not re-dispatch them.
- Platform behaviors: declare `static internalsBehaviors` and read them with `getBehavior()`. Never store them in class fields from `createBehaviors()` (runs inside `super()`, fields reset after).
- `blk-control-ssr` never creates its control; browser-only code is guarded by `isServer`.
